# Блок 3: Владение (Ownership) и заимствование (Borrowing)

## Цель

Понять, как Rust управляет памятью **без сборщика мусора**, используя систему владения (ownership) и заимствования (borrowing), и научиться читать и писать код, который уважает эти правила.

---

## 1. Интуиция: управление памятью без GC

Прежде чем нырять в формальные правила, важно понять **интуицию**, зачем вообще Rustу нужна система владения.

### Как это бывает в других языках

- В языках с **GC (Garbage Collector)**, например Java, C#, Go:
  - Память «собирается» автоматически;
  - Разработчик редко думает, **когда именно** память освободится;
  - Минус — непредсказуемые паузы GC и отсутствие жёстких гарантий на уровне компиляции.

- В C / C++:
  - Память выделяется вручную (`malloc`, `new`) и освобождается вручную (`free`, `delete`);
  - Легко допустить:
    - утечки памяти (забыли `free`);
    - «висячие» указатели (dangling pointers) — память уже освобождена, а указатель ещё используется;
    - двойное освобождение (double free).

Rust идёт **третьим путём**:

- Нет GC;
- Нет ручного `free`;
- Вместо этого есть **компилятор**, который строго проверяет:
  - кто «владеет» данными;
  - как долго эти данные живут;
  - кто может к ним обращаться и когда.

Если правила нарушены — программа **не компилируется**.

### Простая ментальная модель

Представь, что у каждого куска данных есть **владелец**:

- Владелец отвечает за **жизненный цикл** данных;
- Когда владелец выходит из области видимости (scope) — данные автоматически уничтожаются;
- Владелец может **передать владение** другому (move), но тогда сам больше не может использовать эти данные.

Rust «зарубает» на корню многие классы ошибок **на этапе компиляции**, а не в рантайме.

### Мини‑пример для интуиции

```rust
fn main() {
    {
        let x = 5;         // x живёт внутри этого блока
        println!("{}", x); // можно использовать x
    } // здесь x «умирает», память освобождается (на стеке)

    // println!("{}", x); // Ошибка компиляции: x больше не существует
}
```

> Вопрос: чем этот пример отличается от языков вроде JavaScript или Python, где переменные тоже «живут в блоках»?  
> Подумай: где здесь участвует **владение**, а где — просто область видимости?

## 2. Правила владения (Ownership rules)

В Rust есть всего **три базовых правила владения**:

1. У каждого значения в Rust есть **владелец**.
2. В каждый момент времени может быть **только один владелец**.
3. Когда владелец выходит из области видимости, значение **удаляется** (drop).

Эти правила особенно важны для **данных в куче (heap)**, например, для `String`.

### Пример: владение `String`

```rust
fn main() {
    let s = String::from("hello"); // s владеет строкой в куче

    println!("{}", s); // можно использовать s здесь
} // здесь s выходит из области видимости, строка освобождается
```

Rust автоматически вызывает функцию `drop` для `s` в конце области видимости, освобождая память в куче. Тебе не нужно вызывать `free` вручную.

### Move (перемещение) владения

Когда ты присваиваешь `String` другой переменной, **владение передаётся** (move), а не копируется побайтно:

```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1; // владение переходит к s2

    // println!("{}", s1); // Ошибка: value borrowed here after move
    println!("{}", s2);    // OK: теперь s2 владелец строки
}
```

Важно:

- `s1` перестаёт быть валидным после `let s2 = s1;`;
- Rust **не позволяет** использовать `s1` дальше — так он защищает нас от двойного освобождения памяти.

> Вопрос: почему Rust не делает «глубокую копию» строки при `let s2 = s1;`?  
> Как это повлияло бы на производительность, если бы каждая передача строки копировала все байты?

## 3. Стек (Stack) vs куча (Heap)

Чтобы по‑настоящему понять владение, нужно разобраться, **где именно живут данные**.

### Стек: быстрый и простой

Стек — это область памяти с принципом работы **LIFO (Last In, First Out)**:

- Данные добавляются и убираются строго в обратном порядке;
- Размер известных типов (например, `i32`, `bool`, кортеж фиксированного размера) известен **на этапе компиляции**;
- Операции со стеком очень быстрые.

Пример типов, которые обычно живут целиком на стеке:

- Числа: `i32`, `u64`, `f64`;
- Булевы: `bool`;
- Фиксированные кортежи из таких типов: `(i32, bool)`.

```rust
fn main() {
    let x = 5;        // x лежит на стеке
    let y = 10;       // y тоже на стеке
    let pair = (x, y); // кортеж из двух i32 тоже на стеке

    println!("{}, {}", x, pair.0);
}
```

Когда функция `main` завершится, стек просто «отмотается назад», и все эти значения исчезнут **одной операцией**.

### Куча: гибкая, но дороже

Куча — это область памяти для данных, размер или время жизни которых:

- не известны заранее;
- или могут меняться в рантайме.

Пример: `String`:

- На стеке лежит **маленькая структура**: указатель на данные в куче, длина, ёмкость;
- В куче лежат **байты строки**.

```rust
fn main() {
    let s = String::from("hello");
    // s (указатель, длина, ёмкость) на стеке
    // "hello" (байты) — в куче

    println!("{}", s);
} // здесь вызывается drop(s), и память в куче освобождается
```

Работа с кучей дороже по времени, чем со стеком:

- Нужно искать свободный блок памяти;
- Нужно уметь его освободить позже.

### Как это связано с владением?

- Для **стековых типов** (простые числа, маленькие кортежи) копирование обычно дешёвое, и многие из них реализуют `Copy`;
- Для **кучевых типов** (`String`, `Vec<T>`) реальное содержимое лежит в куче, и глубокое копирование может быть дорогим → Rust предпочитает **перемещать владение**, а не копировать всё содержимое.

> Вопрос: почему, как ты думаешь, `String` ведёт себя с move‑семантикой, а `i32` можно свободно копировать?  
> Как это связано с тем, где именно лежат данные — на стеке или в куче?

## 4. Move vs Copy и `Copy` trait

Теперь формализуем разницу между **перемещением (move)** и **копированием (copy)**.

### Move ещё раз, но внимательнее

Когда мы пишем:

```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1; // move

    println!("{}", s2);
    // println!("{}", s1); // ошибка: s1 больше не владелец
}
```

Происходит следующее:

- копируются **данные на стеке** (структура `String`: указатель, длина, ёмкость);
- **не копируются** байты строки в куче;
- предыдущий владелец (`s1`) **становится недействительным**, чтобы избежать двойного освобождения памяти.

Это и есть **move‑семантика**: владение перемещается, старый владелец «обнуляется» с точки зрения компилятора.

### Копирование для простых типов (`Copy`)

Для некоторых типов move не очень удобен — они маленькие и дёшево копируются. Пример:

```rust
fn main() {
    let x = 5;
    let y = x; // здесь x не «инвалидируется»

    println!("x = {}, y = {}", x, y); // оба доступны
}
```

Почему это работает?

- Тип `i32` реализует специальный трейд `Copy`;
- Для типов с `Copy` **присваивание делает побайтовую копию**, а не move;
- Оба значения (`x` и `y`) остаются валидны.

### Правило: `Copy` только для простых значений

Тип может быть `Copy`, если:

- его размер фиксирован и известен на этапе компиляции;
- он не владеет ресурсами в куче;
- все его поля тоже `Copy`.

Примеры `Copy`‑типов:

- все скалярные типы (`i32`, `u32`, `f64`, `bool`, `char`);
- кортежи из `Copy`‑типов: `(i32, bool)`, `(u8, u8, u8)`.

Примеры не‑`Copy`‑типов:

- `String`;
- `Vec<T>`;
- большинство своих собственных структур, которые владеют кучей.

### Пример сравнения: `i32` vs `String`

```rust
fn takes_integer(n: i32) {
    println!("n = {}", n);
}

fn takes_string(s: String) {
    println!("s = {}", s);
}

fn main() {
    let x = 10;
    takes_integer(x); // x копируется (Copy)
    println!("x still usable: {}", x);

    let s = String::from("hello");
    takes_string(s); // s move'ится в функцию
    // println!("s: {}", s); // ошибка: s больше нельзя использовать
}
```
