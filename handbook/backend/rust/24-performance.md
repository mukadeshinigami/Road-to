# Блок 24: Производительность и оптимизация (Performance)

## Цель

Писать **быстрый код** и **профилировать**: бенчмарки (criterion), профилирование (perf, flamegraph), оптимизация аллокаций, zero-copy, кратко SIMD, inline, LTO, layout, профили Cargo.

---

## 1. Benchmarking: criterion

Крейт **criterion** — статистически устойчивые бенчмарки. Группы итераций, сравнение до/после изменений. Результаты в `target/criterion/`. Интеграция с `cargo bench`.

```toml
[dev-dependencies]
criterion = "0.5"

[[bench]]
name = "my_bench"
harness = false
```

В бенчмарке: группа с циклом итераций, замер времени, вывод через criterion. Сравнение двух реализаций — через BenchmarkId и параметризацию.

---

## 2. Профилирование: perf, flamegraph

- **perf** (Linux): `cargo build --release`, `perf record ./target/release/binary`, `perf report`. Показывает, где тратится время (CPU).
- **Flamegraph**: инструментирование + визуализация стека вызовов. Крейты вроде flamegraph или perf + stackcollapse.

Сначала измерить, потом оптимизировать горячие места.

---

## 3. Оптимизация аллокаций

Частые аллокации в горячем цикле — источник накладных расходов. Приёмы: переиспользовать буферы (Vec::clear + повторное использование), предварительно резервировать capacity, избегать клонирования там, где достаточно ссылок или копирования малых структур (Copy). Профилировать до/после.

---

## 4. Zero-copy техники

По возможности не копировать данные: слайсы вместо владеющих коллекций, парсинг в представлении «вид на байты» (например, zerocopy, bytemuck для типизированного просмотра), передача ссылок между слоями. Осторожно с временем жизни.

---

## 5. SIMD (кратко)

Использование векторных инструкций (SSE, AVX) для обработки нескольких элементов за раз. В Rust — через std::simd (nightly), крейты packed_simd или ручной inline assembly. Требует знания целевой архитектуры и выравнивания.

---

## 6. Inline и LTO

- **#[inline(always)]** / **#[inline]** — подсказка компилятору встраивать вызовы; не злоупотреблять.
- **LTO (Link Time Optimization)** в release-профиле: `lto = true` — больше оптимизаций на этапе линковки, дольше сборка, часто быстрее бинарник.

---

## 7. Memory layout и padding

Структуры выравниваются по полям; порядок полей влияет на размер из-за padding. Для плотной упаковки — располагать поля по убыванию размера или использовать repr(packed) (осторожно с выравниванием и доступом). Измерять размер через std::mem::size_of.

---

## 8. Cargo-профили

В Cargo.toml настраивают [profile.release]: opt-level (3, "s", "z"), lto, codegen-units, strip. Баланс между временем сборки, размером бинарника и скоростью выполнения.

---

## 9. Итоги

- Бенчмарки через criterion; профилирование через perf/flamegraph.
- Меньше аллокаций, zero-copy где возможно; SIMD — при необходимости.
- Inline, LTO, порядок полей и профили Cargo для финальной скорости.
